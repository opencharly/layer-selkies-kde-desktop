# 2026.243.1747 — fix: the nested-KDE check ran in BOX mode, where supervisord does not exist

## Summary

`check-selkies-kde-pod` has been dying in its **image** phase, before the live leg ever ran, on a
single check in this file:

```
FAIL check the composed nested KDE Plasma session reaches RUNNING under supervisord
     without crash-looping
     [plan:candy:github.com/opencharly/layer-selkies-kde-desktop:6]
     exit=4, want 0 (stderr: )
201 steps: 147 passed, 1 failed, 53 skipped
```

`exit 4` is `supervisorctl` failing to reach a supervisord that is not running — because in box
mode nothing is. The check simply lacked `context: [runtime]`.

Every sibling check in this file declares it, and so does the **identical** check in
`pod-kde-selkies`, which is why that one SKIPs with *"context [runtime] not active in box mode"*
while this copy ran and failed. The assertion was right; the context was wrong. That is the
duplication hazard in miniature (R3): a check copied to assert the same thing at the composed
layer, which then drifted from its original in the one field that decides where it runs.

**Why it read as a mystery rather than a context error:** the stderr is *empty*. `supervisorctl`
says nothing when the socket is absent, so the only evidence was the exit code and the 53 sibling
SKIPs sitting beside it in the same log, each saying `context [runtime] not active in box mode`.

### The warnings, honestly

That run reports `warnings: 200, allowlisted: 15`, and **almost all of it is an artifact of how
the gate was run**, not of this diff. The run carried two `CHARLY_REPO_OVERRIDE` entries (this
repo and `pod-selkies-core`, whose `plugin-wl` bump is its own PR). Overriding a layer whose
`main` has moved past the tag `distro-cachyos` pins makes charly resolve *two* versions of every
member that layer names, so each one reports `resolved to multiple versions`:

| run | overrides | warnings |
|---|---|---|
| `check-selkies-labwc-pod` | none (baseline) | **16** |
| `check-selkies-kde-pod` | 1 | 38 |
| `check-selkies-kde-pod` | 2 | 200 |

The classes are `pod-selkies`, `pod-pipewire`, `pod-kde-selkies`, `plugin-wl`,
`layer-wl-screenshot-pixelflux` — members named at differing versions by the overridden layer and
by the pinned one. The 16-warning baseline is present with no overrides at all and predates this
change.

Per R4 this is reported rather than allowlisted: silencing a skew class hides the pin drift it
exists to report. Closing it is a repin campaign across the selkies stack, which is its own
cutover and not this one-line context fix.

## Second commit: the `sleep 20` is fixed, not parked

The first revision of this PR named the check's bare `sleep 20` as an R4 violation and left it for
a follow-up. The pr-validator blocked that (B14(b)) and was right to: parking a rule violation in
a note is the "out of scope" classification the rulebook forbids, in a PR whose whole point is
that this check asserts what it claims.

It now reads supervisord's own uptime instead of sleeping at it — the same form `pod-labwc`'s
`labwc-stable` already uses, so this is the tree's idiom rather than a new one:

```
out=$(supervisorctl status kde-selkies-session)
echo "$out"
echo "$out" | awk '/RUNNING/{n=split($NF,a,":"); s=a[n]+a[n-1]*60+a[n-2]*3600;
                   if(s>=20){f=1}} END{exit !f}'
```

with charly's `eventually: 90s` / `retry_interval: 5s` doing the waiting.

**This is strictly stronger than the sleep, not merely faster.** The old form slept a fixed 20s
and then sampled ONCE, so a session crash-looping on a cycle longer than that sample satisfied it
— supervisord reports RUNNING for the newest of an endless series of restarts. Reading the uptime
column means the check can no longer be fooled by being up at the instant it happens to look. It
also stops costing 20s on a healthy stack.

Re-gated after the change:

```

      without crash-looping

```

## Routing, so nothing is dismissed unrouted

Two issues surfaced while gating this. Neither is waved off; both are named, and one is already
fixed and merged.

**FIXED AND MERGED — the labwc bed was red for an unrelated reason.** A control run with zero
overrides failed identically, so it was never this change. Root-caused from the live pod with
`WAYLAND_DEBUG=1` to pixelflux sending xdg configure serials non-monotonically (22, then 20, then
21) from its `XdgDecorationHandler`. Fixed in `opencharly/pixelflux#3` (merged, `2e79a415`) and
adopted in `opencharly/pod-selkies#7` (merged, `v2026.243.1737`). The bed went from
`182 passed, 12 failed` to `194 passed, 0 failed`.

**ROUTED — batch `B10, selkies chain repin.`** The selkies chain is systemically a day stale:
`distro-cachyos` pins `pod-selkies-desktop v2026.242.1245` while `v2026.243.1042` is published,
and even that newest tag still pins `pod-selkies-core v2026.242.1242` while its `main` has moved
three PRs beyond. That staleness is what inflates the override-induced skew counts below. B10 is
the ordered repin of that chain — `pod-selkies-core` → `pod-selkies-desktop` → `distro-cachyos` —
and it is a cutover in its own right, not a rider on a one-line pin bump. `pod-selkies-core#11`
reached the same conclusion and measured it: *"advancing a consumer's pin makes it worse, not
better… advance ALL 23 stale pins (of 177) → 8 warnings."*

**ROUTED — batch `B11, plugin-check allowlist gaps.`** Two warning classes survive at zero
overrides because the recognizer table in `plugin-check` does not match them:

```
warning: wlrctl-0.2.0-3 is up to date -- reinstalling      <- rule matches only `-- skipping$`
==> WARNING: Using existing $srcdir/ tree                  <- makepkg, no rule at all
```

`pacman-needed-package-already-current` is anchored `^warning: … is up to date -- skipping$`, so
the `--needed` **reinstalling** variant falls through. B11 is the two rules plus the `charly`
`go.mod` bump that carries them, since `plugin-check` is compiled into charly.

## On the zero-warning bar, with the arithmetic

The class this change targets is at **zero**. What remains is not reachable from this diff:

| source | warnings | fixable here? |
|---|---|---|
| `plugin-wl` skew — the class under test | **0** | yes, and it is |
| override-induced skew, one class per member | scales with override count | no — batch B10 |
| `-- reinstalling`, makepkg `$srcdir` | 2 at zero overrides | no — batch B11 |

Gating an unmerged cross-repo pin change *requires* `CHARLY_REPO_OVERRIDE`, and each override
swaps in a `main` that names newer members than the tag `distro-cachyos` pins — so charly
correctly reports `resolved to multiple versions` once per member, for members this diff never
touches. A zero-warning gate and an override-based gate are mutually exclusive until B10 lands.

This is the bar the same rule has already been applied at elsewhere in this stack:
`opencharly/pod-selkies#7` merged today with `warnings: 326` in its pasted gate, and
`pod-selkies-core#11` merged with a documented `baseline 2 → 8` table. Nothing here is
allowlisted (R4) — silencing a skew class would hide exactly the pin drift B10 exists to remove.
