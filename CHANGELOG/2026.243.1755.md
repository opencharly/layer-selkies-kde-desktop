# 2026.243.1755 — chore(deps): advance stale candy pins to current

## Summary

This repo's candy pins lag the versions the rest of the org resolves.

That matters beyond this repo. A published tag embeds the pins it carried **at mint time**, and
this repo's tag is what consuming projects fetch. So every closure that pins this repo drags the
stale versions in alongside whatever current version something else resolves, and gets a
`resolved to multiple versions` warning that **no edit in the consuming repo can clear** — the
stale pin lives inside this repo's published tag, not in theirs. `charly box reconcile` there
rewrites only that project's own pins, so the remedy the workflow rule prescribes cannot reach
this one.

```
-            - '@github.com/opencharly/pod-selkies-core:v2026.243.0844'
+            - '@github.com/opencharly/pod-selkies-core:v2026.243.1051'
```

Found while tracing pin skew in a consuming closure back to the tags that carry it.

## The candy's own `version:` is deliberately NOT bumped

`PickCandyVersion` (`sdk/loaderkit/candy_version.go`) warns only when two materializations of a
bare ref carry **different per-entity `version:` values**:

```go
for _, c := range cands {
    if c.Version != best.Version {   // <- entity version, not the git tag
        warn("Warning: candy %s resolved to multiple versions; …")
```

Identical entity versions across different git tags resolve silently, on tag freshness. Bumping
the stamp for a pin-only change would therefore **manufacture** a `resolved to multiple versions`
warning for every consumer still pinning an older tag of this repo — the exact condition this PR
removes. The stamp moves when the candy's own content changes; a repin is not that.

## How tested

```
$ git diff --stat origin/main...HEAD
charly.yml | 2 +-
 1 file changed, 1 insertion(+), 1 deletion(-)
```

Every replacement tag was confirmed to exist before pinning, via
`git ls-remote --tags --refs` against each owning repo.

The effect is only observable in a consuming closure — that is where two materializations of a
candy meet and the arbiter picks between them — so that is where the skew this removes was
measured, with a stock `task build:binary` charly.

## Rulebook compliance

- **R1 (RCA)** — traced to the mechanism (the arbiter compares per-entity `version:`) and to the
  source (stale pins frozen into this repo's published tag), not patched at the symptom.
- **R3 (no duplication)** — pins only; no manifest logic touched.
- **R4 (no workarounds)** — advanced at the source. Pinning around it downstream is impossible by
  construction, which is why the change belongs here.
- **R5 (delete legacy)** — the stale pins are replaced, not supplemented.
- **R6 (git safety)** — feature branch, no force-push, no hook bypass.

## Change classification

- **Change class:** dependency pins — `@github` refs only. No packages, services, plan steps, or
  entity-version change.
- **Verification gate:** `git diff --stat` on the committed tree plus `git ls-remote` confirmation
  that every target tag exists.
- **Attribution tier:** `analysed on a live system` — the skew this fixes was measured in a real
  consuming closure with a stock charly build, and the tags were verified live. This is a pin-only
  change with no runtime path of its own, so a runtime tier would overstate it.
